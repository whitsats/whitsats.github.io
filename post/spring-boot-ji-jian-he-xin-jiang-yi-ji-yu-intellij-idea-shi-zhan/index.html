Spring Boot 极简核心讲义 (基于 IntelliJ IDEA 实战)

2026-06-11

作为一门现代化的工程课程讲义，本文将抛弃一切老旧冗余的理论，直接从架构认知和 IDEA 实战切入，带你完成从 0 到 1 构建标准化后端 API 的全过程。

一、 核心架构认知：现代后端的“流水线”

在编写任何一行代码前，必须建立起现代 Java 后端工程的规范分层认知。不要把所有代码揉在一起，要像工厂流水线一样分工明确。

1. 核心流程图解 (层级交互)

这就是一个标准后端 API 从接收请求到响应的全过程，严格遵循“单向调用”原则。

graph TD
    Client[前端 / App] -->|1. 发起 HTTP 包含 JSON| Controller
    Controller -->|2. DTO 封装参数| Service
    Service -->|3. 核心业务处理| Mapper
    Mapper -->|4. Entity 映射| Database[(MySQL)]
    Database -->|5. 查询结果集| Mapper
    Mapper -->|6. Entity 返回| Service
    Service -->|7. 转化为 VO| Controller
    Controller -->|8. 响应 JSON| Client

2. 数据载体图解 (Data Models)

数据在各个层级之间流转时，必须“穿不同的衣服”（即使用不同的类）。

    JSON -->|进| DTO
    DTO -.->|提取与转换| Entity
    Entity -->|保存| Table
    
    Table -->|查询| Entity
    Entity -.->|脱敏与包装| VO
    VO -->|出| JSON
  • Entity / DO (Data Object)：数据库的绝对镜像。数据库表里有什么列，它就有什么属性。它只存在于 Service 层和数据库之间。
  • DTO (Data Transfer Object)：数据传输对象。专门用于接收前端通过 JSON 传过来的参数。例如注册接口，前端传来的密码会在 DTO 中，但绝不该出现在返回给前端的 VO 中。
  • VO (View Object)：视图对象。后端处理完业务后，专门打包返回给前端展示的数据结构。

3. 动作执行 (Layers)

所有的业务动作严格遵循以下“三板斧”流水线：

  1. Controller 层 (调度大厅)：只负责对外暴露 URL 接口，接收前端传来的 DTO，校验无误后，把活儿派发给 Service。最后拿到 Service 的结果，包装成 VO 变成 JSON 返回给前端。
  2. Service 层 (业务大脑)：这里写所有的核心业务逻辑（例如计算折扣、校验权限）。它是最重要的地方。
  3. Mapper 层 / DAO (数据库搬运工)：纯粹负责和数据库打交道。在现代开发中（例如使用 MyBatis-Plus），这一层你甚至不需要写 SQL，框架自带了所有的增删改查。

二、 第一步：在 IDEA 中极速创建工程

打开你的 IntelliJ IDEA，遵循以下黄金步骤：

  1. 菜单栏选择 File -> New -> Project...
  2. 左侧选择 Spring Initializr。
  3. 配置基础信息：
    • Type: Maven
    • Java: 17 (推荐)
    • Packaging: Jar
  4. 【最关键的一步】勾选依赖 (Dependencies)，相当于配置脚手架插件：
    • Web -> 勾选 Spring Web (提供核心 API 能力和内嵌 Tomcat)
    • Developer Tools -> 勾选 Lombok (神器！自动帮你写 Get/Set 方法)
    • SQL -> 勾选 MySQL Driver (数据库驱动) 和 MyBatis-Plus Framework (现代 DAO 层神器)
  5. 点击 Create，IDEA 会自动下载依赖并构建项目。

三、 第二步：实战演练（编写注册 API）

假设我们要写一个“用户注册”接口。我们将严格按照刚才讲的分层架构进行开发。

1. 定义数据载体 (DTO, Entity, VO)

[!TIP]
注意到了吗？我们使用了 @Data 注解，这是 Lombok 提供的神器，它在编译时会自动帮你生成 get/set 方法，保持代码极其干净。

// 1. DTO: 接收前端传来的注册信息
@Data
public class UserRegisterDTO {
    private String username;
    private String password;
}

// 2. Entity: 映射数据库的表 (t_user)
@Data
@TableName("t_user") // MyBatis-Plus 注解，指定表名
public class UserEntity {
    private Long id;
    private String username;
    private String password; 
    private LocalDateTime createTime;
}

// 3. VO: 返回给前端的信息（注意：绝对不返回密码！）
@Data
public class UserVO {
    private Long id;
    private String username;
}

2. 编写 Mapper 层 (替代传统的 DAO)

在现代开发中，DAO 层变得极其简单，只需继承 BaseMapper，你瞬间拥有了全部的单表增删改查能力。

import com.baomidou.mybatisplus.core.mapper.BaseMapper;
import org.apache.ibatis.annotations.Mapper;

@Mapper // 告诉 Spring 这是一个数据库交互接口
public interface UserMapper extends BaseMapper<UserEntity> {
    // 空空如也？是的！BaseMapper 已经包含了 insert(), selectById() 等数十个方法！
}

3. 编写 Service 层 (核心业务逻辑)

业务逻辑必须放在 Service 中处理（比如检查用户名是否冲突，将 DTO 转换为 Entity 保存）。

@Service // 注册到 Spring 容器中
public class UserService {

    private final UserMapper userMapper;

    // 构造器注入 (依赖注入 DI 实战)
    public UserService(UserMapper userMapper) {
        this.userMapper = userMapper;
    }

    public UserVO register(UserRegisterDTO dto) {
        // 1. 将 DTO 转为 Entity (通常会用工具类如 MapStruct 或 BeanUtils)
        UserEntity entity = new UserEntity();
        entity.setUsername(dto.getUsername());
        entity.setPassword(dto.getPassword()); // 实际开发中这里应该加密
        entity.setCreateTime(LocalDateTime.now());

        // 2. 保存入库 (直接调用自带方法)
        userMapper.insert(entity);

        // 3. 将结果转为 VO 返回
        UserVO vo = new UserVO();
        vo.setId(entity.getId());
        vo.setUsername(entity.getUsername());
        
        return vo;
    }
}

4. 编写 Controller 层 (对外暴露接口)

最后一步，将写好的业务暴露成 HTTP 接口。

@RestController // 声明这是一个返回 JSON 的控制器
@RequestMapping("/api/users") // 统一路由前缀
public class UserController {

    private final UserService userService;

    // 构造器注入
    public UserController(UserService userService) {
        this.userService = userService;
    }

    @PostMapping("/register") // POST 接口
    public UserVO register(@RequestBody UserRegisterDTO dto) {
        // 接收参数 -> 移交业务层 -> 直接返回给前端
        return userService.register(dto);
    }
}

四、 总结与自测

当你运行程序的 main 方法后，由于 Spring Boot 内嵌了 Tomcat 服务器，它会直接在 8080 端口启动。

整个数据流向完美闭环：
JSON ➡️ DTO ➡️ Controller ➡️ Service ➡️ Entity ➡️ Mapper ➡️ 数据库 ➡️ Service ➡️ VO ➡️ Controller ➡️ JSON

[!IMPORTANT]
思考题：在上面的代码基础上，如果我的项目中还需要加一个“根据 ID 查询用户信息”的接口，按照这个架构，我需要在刚才的哪几个类里补充哪些代码？
